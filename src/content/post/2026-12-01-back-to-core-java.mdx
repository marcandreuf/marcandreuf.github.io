In August I wrote about [a year of shipping software while barely looking at the code](/blog/2026-08-13-no-code/). Four projects, two of them full SaaS products, all generated with AI, all covered by tests, all used by real people. I set it up as an experiment to see how far the tools could be pushed, and the honest answer is: very far.

I could create more, and faster, than at any point in my career.

And yet I have spent the last two months doing the opposite. I opened a repository of Java exercises I wrote between 2014 and 2021, and I started rewriting it by hand.

This post is about why.

## More, Faster, and Further Away

The experiment worked. That is not in question. What I did not expect was how the work would feel once the novelty was gone.

Everything I shipped looked right. The tests were green, the users were happy, the features arrived. But the whole thing felt alienated from me, from the problem, and from the solution. I knew _what_ the software did. I did not really know _how_ it did it, and so I did not know where it would bend and where it would break.

That distance has a cost, and it shows up at the worst possible moment: when a user asks for something new. When I have written the code myself, a new requirement lands on a model I already carry in my head. I can see where it goes, what it touches, and what it will cost. When the code was generated, a new requirement is the start of an investigation. I am reading my own system like a stranger's.

What I love about this job has always been solving problems, and spending time writing code that feels good, that solves the problem, and that I can quickly adapt or extend when the requirements move. A year of generating solutions gave me the first part without the rest.

Maybe that is nostalgia. I have asked myself that more than once. But I do not think it is only that.

## Match the Verification to the Blast Radius

In the August post I argued that most of us are shipping the next CRM feature, not avionics, and that we should match the verification to the blast radius. I still believe that. For a lot of software, generated code, generated tests and real users validating it is the right trade.

But I underweighted one dimension of blast radius: **time**.

A prototype, an internal tool, a campaign landing page, a short-lived integration: these can be generated, validated and thrown away, and nobody will miss the craft. An enterprise system is different. It lives for ten or twenty years. It outlives its team, its framework versions and usually its original requirements. The question for that kind of system is not "does it work today?" but "can someone change it safely in 2035?"

That someone needs to understand it. And understanding is exactly what I was trading away.

So this is not me taking back the August post. It is me drawing the line it left vague. **AI code generation is very useful for many non critical solutions. For long lived enterprise solutions, I want an engineer in the loop who can read, reason about and own every line, and I want that engineer to be me.**

## Why Java, Why Now

I started my career as a Java developer. For a long time I drifted away from it, through test automation, architecture, infrastructure and, more recently, a lot of TypeScript. Coming back is partly personal. But I also think Java is well positioned for what comes next.

The first wave of AI was about generating things: text, images, code, prototypes. The second wave, as I see it, is about putting AI to work inside the systems businesses already run, as assistants and agents that augment people so they can achieve more, faster, and with better software. Those systems, the banks, insurers, logistics platforms and public administrations, run on the JVM to a degree that is easy to forget if you spend your time in startup land.

And the language has been quietly getting ready:

- **The type system is a verifier.** Records and sealed types let the compiler check that every case is handled. When I worked through pattern matching in the katas, the lesson I wrote down was that adding a variant to a sealed type has a wide effect across files, but the compiler and the IDE tell you every single place before anything runs. That is exactly the safety net you want when an agent, or a colleague, is changing code you did not write.
- **Virtual threads** make the I/O-heavy, wait-on-a-remote-call shape of agentic workloads cheap to write in plain, blocking, readable code.
- **The ecosystem is there**, with Spring AI and LangChain4j bringing model and agent integration to the frameworks enterprise teams already use.
- **Backwards compatibility** is a feature you only appreciate when your system has to survive a decade of upgrades.

None of this makes Java the answer to everything. It makes it the right tool for the right problem, and the problem I care about most is software that has to last.

## AI Wrote the Curriculum. I Write the Code.

Here is the part I find most interesting. I did not go back to Java _instead of_ using AI. I used AI to find my way back.

The repository is [java-katas](https://github.com/marcandreuf/java-katas), and it is public. It holds exercises I wrote between 2014 and 2021: real code with real habits in it, pre-diamond generics, hand-rolled `finally` blocks, `wait` and `notifyAll`, swallowed `InterruptedException`, and a couple of genuine bugs.

I asked Claude Code to analyse that code against the language as it is today, find my knowledge gaps, and build a custom curriculum around them, with theory and exercises that land on my own files. What came back is two tracks:

- **A modernization track**, 35 documents, one concept each: records, sealed types, pattern matching, virtual threads, the memory model, streams, `java.time`, stream gatherers, the foreign function and memory API, scoped values, structured concurrency, and more. It has two orderings: by concept, smallest change first, and by release, every developer-facing feature from Java 8 to Java 26 in the version it landed.
- **A data structures and algorithms track**, twelve stages, built on a thesis I agree with completely: almost none of the algorithms are load-bearing, and almost all of the contracts are. Nobody shipping Java implements a hash table. What ships, again and again, is a `contains` inside a loop, a key whose `hashCode` disagrees with its `equals`, a comparator that overflows, and a recursion whose depth is the size of the input.

The rules are strict, and I like them:

1. **No test, no rewrite.** Twenty of the thirty-two old classes had never had a test. The first commit on each of them is a test that asserts what the code does today, bugs included.
2. **One concept per commit.** The diff is the deliverable.
3. **Every document ends with "what got worse"**, and I have to fill it in. Knowing where a feature hurt is worth more than knowing its name.

AI did the part it is genuinely brilliant at: reading a lot of material, mapping what I knew against what exists now, and structuring a path through it. I do the part that cannot be delegated if the goal is to actually know it: writing the code, breaking it, and deciding what I think.

## What the Old Code Taught Me Already

Two findings, before I had changed anything of substance.

**My binary search was broken, and its tests were green.** `BinarySearch.java` cannot find five of the twelve elements in its own test fixture. Eight tests, all passing. The algorithm was the easy part; the part nobody checked was the part that was wrong. That is the whole DSA track in one file.

**A test stayed disabled for twelve years.** `FairWorkloadTest` was switched off in 2014 with a note saying the cause was never found. It was still off in 2026. Now every skipped test in the repo must carry a reason that names the document that owns it.

I am working through the track in order. Records, pattern matching, switch expressions and `var` are done, and I am in the middle of virtual threads. It is slow. It is also the most fun I have had with code in a long time.

## The Engineer in the Loop

I do not think the future is humans writing every line, and I do not think it is agents writing every line either. The second wave is about augmentation: people and AI working on the same system, each doing what they are good at.

For that to work on software that matters, the human in the loop has to be good. Not good at prompting. Good at the language, the runtime, the contracts and the trade-offs, so they can tell when the generated code is right, when it only looks right, and how to change it when the users ask for something new.

That is what I am rebuilding. One kata, one concept, one commit at a time.
